# 材料元信息版本设计

## 问题与边界

教师上传材料后，Core 已把文件复制到受管目录，并在 `education_intake_state.json` 保存稳定材料 ID、文件哈希、大小、名称、类型、学科和班级。桌面端只能删除或打开 AI 对话，无法直接改几个字；现有“操作历史”只证明最初接入发生过，不能恢复字段值。

材料文件和材料元信息必须继续由同一 Core 记录管理。元信息修改不重命名、不替换、不重新上传文件，也不改动 `source_hash`、文件大小、受管路径、staging 身份、来源和证据。

## Core 状态与合同

在现有材料记录内增加私有 `metadata` 状态，而不是建立第二份当前材料库。新接入材料从 revision 0 开始；旧记录在第一次修改时从当前四个字段建立 revision 0 基线。可编辑字段只有：

- `title`
- `kind`
- `subject`
- `class_id`

每次真实变化保存连续 revision、修改前后值、受影响字段、来源、请求 ID、时间和内容绑定的版本 ID。单材料最多保留50条版本；总版本、回执和状态文件均有上限，超限时只裁剪最旧历史，不改变当前值。普通 `teacherMaterials` 投影只返回当前值、revision、history count 和更新时间；旧值仅通过 `workspace-resources` 的显式材料历史参数读取。

Core 新增 `material-metadata` 操作，支持 `update` 与 `restore`。请求必须携带材料稳定 ID和当前 revision；重复请求以完整语义对账，同一请求不能改指另一字段或版本。编辑操作在实体删除锁内再取得材料接入锁，因此删除、恢复和元信息修改不能交错提交。已删除材料拒绝修改和历史读取，tombstone 恢复后保留原 revision 与版本。

## 下游联动

元信息保存后重写现有 `material_candidates.json` 兼容镜像并立即运行节奏刷新。名称变化更新课前准备中的“可用材料”；学科或班级变化决定材料是否仍匹配对应课次。课次 task ID保持不变，来源 fingerprint 和材料版本证据随 revision 变化。显式绑定材料的 G1 仍在模型调用前核对材料记录哈希和文件字节，旧执行不能跨 revision 继续。

## 桌面交互

已接入材料抽屉增加“修改信息”，直接编辑名称、类型、学科和班级；保存与取消都留在当前材料。AI 协作继续打开全局会话草稿，并把当前四个字段和明确教师输入位置带入对话。

“信息历史”按需显示每次修改的完整前后值。恢复按钮明确为“恢复修改前/恢复修改后”，恢复会同时替换四个字段并形成更高 revision。保存、恢复和外部更新都用同一 revision 的公开材料投影与私有历史对账后再更新页面；过期抽屉提示刷新，不覆盖别人刚完成的修改。

## 验收

Core 隔离流程覆盖旧材料迁移、直接修改、无变化更新、版本恢复、请求重放、过期 revision、同请求换意图、删除后拒绝、tombstone 恢复、历史裁剪和重启重读。材料文件路径、哈希、大小和字节在所有操作前后保持一致。

实际桌面页面完成修改、取消、保存、历史查看、两侧恢复、删除恢复和刷新；材料列表、分类、课前准备摘要及显式绑定任务读取同一 Core 元信息。开发版通过后合并 Core 与 Desktop PR；安装版和跨平台交互继续由下一发布验收，不用源码证据替代。
