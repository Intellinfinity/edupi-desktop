# R08/R10 Core 事实生命周期与对象联动设计

## 问题

Desktop 已验证读取 `education_fact_v1`，但只能展示事实。Core 已有候选审核、已确认事实修订、删除和恢复能力，桌面桥接没有入口，导致待确认数量漏掉事实，学生档案与教学依据也无法把老师的判断写回同一事实对象。

## 边界

- Core 继续拥有事实状态、revision、冲突和写入锁；Desktop 不写 `education_facts_v1.json`，也不从文字重新推断事实。
- 新增 `education-facts` 桥接操作：`review`、`modify`、`delete`、`restore` 和只读 `list_deleted`。请求严格限字段、限长度并绑定当前 revision；响应只返回受限回执或删除列表，始终 `external_send: false`。
- 重放由事实当前状态与最后一条 Core review 记录对账。只有同一旧 revision、动作、审核人、备注和目标值完全一致时返回 replay；其他旧请求返回冲突。
- 接受冲突事实必须明确携带被替换的已确认事实 ID。Desktop 从 Core conflict 投影中显示“接受并替换”，不静默挑选多个冲突。
- 已确认事实的修改继续使用 Core 稳定内容 ID：旧事实进入 superseded，新事实保留来源并进入 accepted。删除后从公开投影移除，私有删除列表提供跨刷新恢复。

## 桌面交互

- 待我确认纳入 Core 事实候选；卡片显示对象、谓词、值、来源和冲突，提供接受、暂缓、拒绝。
- 学生档案显示该学生候选与已确认事实；候选可审核，已确认事实可直接修改或删除。教学依据复用同一操作组件。
- 观察与洞察数据库纳入 Core 事实行与明确状态筛选，来源继续来自 Core observation/source IDs；修改或审核后通过返回的完整教育快照同步各入口。
- 删除成功后保留撤销入口；重新进入页面时可按需读取 Core 删除列表恢复，不用浏览内部文件。

## 验收

- Core 进程测试覆盖审核三态、冲突替换、修改产生新 ID、删除/恢复、响应丢失重放、旧 revision、重启和容量边界。
- Desktop E2 覆盖候选审核、学生与教学同步、修改后观察数据库同步、删除后各入口消失、刷新后恢复及来源不变。
- 实际页面完成同一事实在待确认、学生、教学、观察四个入口的往返；刷新后状态保持，未向真实学生写测试事实。
